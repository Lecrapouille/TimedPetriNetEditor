# 12. 🏗️ Génération de code


[![fr](https://lecrapouille.github.io/icons/fr.png)](../fr/12-Code-Generation.md) [![en](https://lecrapouille.github.io/icons/en.png)](../en/12-Code-Generation.md)

**Ce que vous allez apprendre**

- transformer un réseau en squelette d'un programme C++ pour le runtime : le réseau construit dans le code, une fonction par transition à remplir ;
- transformer les GRAFCET d'un document en un en-tête C++ qui les exécute sur un ordinateur ou sur un Arduino, sans bibliothèque ;
- comment le code généré est vérifié par rapport à l'éditeur.

**Prérequis** : [11. Le runtime](11-Runtime.md) pour la première partie, [9. GRAFCET](09-GRAFCET.md) (et [10. GEMMA](10-GEMMA.md)) pour la seconde.

Les deux se trouvent dans *File > Export*, choisis selon l'extension du fichier :

| Export | Extension | Pour | Ce que vous obtenez |
|--------|-----------|------|---------------------|
| C++ functions for the runtime | `.cpp` `.cc` `.cxx` | réseaux de Petri, réseaux de Petri temporisés | un programme utilisant `libTimedPetriRuntime` ([chapitre 11](11-Runtime.md)) |
| C++ GRAFCET (Arduino, computer) | `.hpp` `.h` `.hh` `.h++` | les GRAFCET du document | un en-tête sans dépendance, pour un micro-contrôleur |

Pourquoi deux ? Le runtime exécute n'importe quel réseau de Petri et appelle vos fonctions ; il a besoin de la bibliothèque standard C++ et de C++20. Un GRAFCET a ses propres règles (IEC 60848), et une petite carte (un Arduino Uno : 2 Ko de mémoire) n'a pas de bibliothèque standard : pour elle, l'éditeur écrit tout le moteur de vos GRAFCET en code plain.

## 1. Le squelette d'un programme pour le runtime

### 1.1 Ce qui est généré

L'export du pick and place ([`PickAndPlace.json`](../../examples/Runtime/PickAndPlace/PickAndPlace.json)) en `pick_and_place.cpp` donne ce fichier, complet :

```c++
// Generated by TimedPetriNetEditor from the net "Pick and place".
// Fill the functions of the transitions, then build the program with the runtime:
//   g++ -std=c++20 -I<TimedPetriNetEditor>/src pick_and_place.cpp
//       -L<TimedPetriNetEditor>/build -lTimedPetriRuntime -lTimedPetriNet -pthread
// With -DTPNE_DEBUG -lzmq it publishes its journal on tcp://*:5556: the editor
// shows it (Debug > Connect).

#include "Runtime/Runtime.hpp"
#ifdef TPNE_DEBUG
#  include "Runtime/JournalPublisher.hpp"
#endif

#include <cstdlib>
#include <iostream>

using namespace tpne;

namespace pick_and_place {

//------------------------------------------------------------------------------
//! \brief The net, built in the code.
Net makeNet()
{
    Net net(TypeOfNet::PetriNet);
    net.name = "Pick and place";
    [[maybe_unused]] Place& p0 = net.addPlace(1u, "Ready");
    [[maybe_unused]] Place& p1 = net.addPlace(0u, "Seen");
    [[maybe_unused]] Place& p2 = net.addPlace(0u, "Held");
    [[maybe_unused]] Place& p3 = net.addPlace(0u, "Done");
    [[maybe_unused]] Transition& t0 = net.addTransition("detect");
    [[maybe_unused]] Transition& t1 = net.addTransition("grasp");
    [[maybe_unused]] Transition& t2 = net.addTransition("place");
    [[maybe_unused]] Transition& t3 = net.addTransition("retry");
    net.addArc(p0, t0);
    net.addArc(t0, p1);
    net.addArc(p1, t1);
    net.addArc(t1, p2);
    net.addArc(p2, t2);
    Arc* arc = net.findArc(p2, t2);
    arc->color = net.colors.add("Success");
    net.addArc(t2, p3);
    net.addArc(p2, t3);
    arc = net.findArc(p2, t3);
    arc->color = net.colors.add("Failed");
    net.addArc(t3, p1);
    return net;
}

//------------------------------------------------------------------------------
//! \brief detect: takes Ready, gives Seen.
Color detect()
{
    // TODO: what detect does.
    return Success;
}

//------------------------------------------------------------------------------
//! \brief grasp: takes Seen, gives Held.
//! Its result chooses what comes next: Failed (retry), Success (place).
Color grasp()
{
    // TODO: what grasp does.
    return Success;
}

//------------------------------------------------------------------------------
//! \brief place: takes Held, gives Done.
Color place()
{
    // TODO: what place does.
    return Success;
}

//------------------------------------------------------------------------------
//! \brief retry: takes Held, gives Seen.
Color retry()
{
    // TODO: what retry does.
    return Success;
}

} // namespace pick_and_place

//------------------------------------------------------------------------------
int main()
{
    Net const net = pick_and_place::makeNet();
    Runtime::Options options;
#ifdef TPNE_DEBUG
    JournalPublisher publisher(net);
    options.journal = [&publisher](LogEntry const& entry) { publisher.publish(entry); };
#endif
    // The functions run on a pool of threads (InlineExecutor: in the thread of run()).
    Runtime runtime(net, std::make_shared<ThreadPoolExecutor>(4u), options);
    runtime.on("detect", pick_and_place::detect);
    runtime.on("grasp", pick_and_place::grasp);
    runtime.on("place", pick_and_place::place);
    runtime.on("retry", pick_and_place::retry);
#ifdef TPNE_DEBUG
    publisher.manifest(runtime);
#endif

    // Ends with Success when the tokens reach the goal, else when nothing
    // can fire any more (Deadlocked).
    auto instance = runtime.instantiate("main", {}, { { "Done", Success } });
    Color const result = runtime.run(*instance);
    std::cout << net.name << ": " << net.colors.name(result) << std::endl;
    return (result == Success) ? EXIT_SUCCESS : EXIT_FAILURE;
}
```

Lisez-le du haut :

- **`makeNet()`** construit le réseau dans le code : places avec leurs jetons, transitions, arcs avec leurs poids, types, couleurs et durées, capacités, priorités, délais. Une carte n'a pas de système de fichiers, et le programme ne dépend plus du fichier JSON. Les positions du dessin ne servent pas.
- **Une fonction par transition**, nommée d'après sa légende (transformée en identifiant C++), dans un espace de noms nommé d'après le fichier. Son commentaire dit ce qu'elle prend et ce qu'elle donne, et, quand les arcs suivants demandent des couleurs, quel résultat mène où : ici `Failed (retry), Success (place)`.
- **`main()`** crée le runtime sur un pool de 4 threads, lui donne les fonctions, et exécute une instance jusqu'à son **objectif** : les places sans arc de sortie (ici `Done`). Changez l'exécuteur, l'objectif, le nombre d'instances selon vos besoins ([chapitre 11](11-Runtime.md)).

Le fichier généré se compile et tourne tel quel (chaque fonction renvoie `Success`) :

```text
$ g++ -std=c++20 -I<TimedPetriNetEditor>/src pick_and_place.cpp \
      -L<TimedPetriNetEditor>/build -lTimedPetriRuntime -lTimedPetriNet -pthread -o pick
$ ./pick
Pick and place: Success
```

### 1.2 Le remplir

Écrivez le code de chaque action dans sa fonction, et renvoyez son résultat. Le pas à pas du [chapitre 11](11-Runtime.md#8--from-the-drawing-to-a-running-robot) remplit le pick and place avec une pince qui glisse une fois :

```text
camera: object seen
gripper: slipped
gripper: holding
arm: placed
Pick and place: Success
```

Une transition qui doit franir tout de suite, sans rien faire (`retry`), peut garder sa fonction générée, ou perdre sa ligne `runtime.on()` : une transition sans fonction franit immédiatement.

### 1.3 Le déboguer

Ajoutez `-DTPNE_DEBUG` et `-lzmq` : le programme publie son journal sur `tcp://*:5556`, et l'éditeur l'affiche en marche ([chapitre 13](13-Debugging.md)) :

```sh
g++ -std=c++20 -DTPNE_DEBUG -I<TimedPetriNetEditor>/src pick_and_place.cpp \
    -L<TimedPetriNetEditor>/build -lTimedPetriRuntime -lTimedPetriNet -lzmq -pthread -o pick
```

### 1.4 Quand vous changez le réseau

L'export réécrit tout le fichier. Gardez les fonctions que vous avez écrites dans un autre fichier (déclarez-les, et effacez les générées), ou copiez le nouveau `makeNet()` dans votre programme.

*File > Export* ne propose pas cet export pour un GRAFCET : le runtime ne lit ni réceptivités ni actions. Pour un GRAFCET, utilisez la section suivante.

## 2. Le code C++ des GRAFCET

### 2.1 Le contexte

Une vidéo française, [*Programmation d'un Grafcet en C pour Arduino*](https://youtu.be/v5FwJvtGaEw), écrit un GRAFCET à la main en C pour un Arduino : un booléen par étape, les réceptivités en `if`, les actions dans un `switch`. C'est long et source d'erreurs, et le résultat suit rarement les règles de la norme (plusieurs transitions qui franissent ensemble, recherche de la situation stable, temporisations, actions mémorisées). L'éditeur écrit ce code pour vous, et le code suit les mêmes règles que sa simulation.

### 2.2 Ce qui est pris en charge

Tout ce que la simulation de l'éditeur exécute ([chapitre 9](09-GRAFCET.md)) :

- les **règles d'évolution** de l'IEC 60848 : toutes les transitions qui peuvent franir franissent ensemble, dans tous les graphes du document ; la recherche de la situation stable (les graphes évoluent jusqu'à ce que plus rien ne puisse franir, puis les actions sont calculées) ; après 256 évolutions sans situation stable, `cycle()` renvoie `false` ;
- **réceptivités** avec et, ou, non, les étapes (`X3`), les étapes des autres graphes (`Production:X3`), **fronts** (`↑a`, `↓a`), **opérateurs de temps** (`3s/X2`, `2s/a/500ms`), comparaisons d'entiers (`[Temperature >= 80]`), et le **délai** d'une transition ;
- **actions** avec leurs qualificateurs `N`, `S`, `R`, `D`, `L`, `SD`, `DS`, `SL`, `P1`, `P0`, leurs durées et leurs **conditions** ;
- **ordres de forçage** entre graphes (une GEMMA : `Production{init}`, `{2,5}`, `{}`, `{*}`).

Les noms des entrées doivent être des identifiants C (`sensor_2`, pas `sensor 2`) ; un nom de sortie devient un seul (`Left Motor` → `Left_Motor`). Une réceptivité avec une erreur de syntaxe est refusée, avec son message.

### 2.3 Tutoriel : le feu tricolore allemand

[`GermanTrafficLights.json`](../../examples/GRAFCET/GermanTrafficLights/GermanTrafficLights.json) est un GRAFCET de quatre étapes : vert 3 s, jaune 1 s, rouge 3 s, rouge et jaune 1 s.

![Feu tricolore allemand](pics/12-GermanTrafficLights.png)

*Le GRAFCET en marche dans l'éditeur : l'étape 2 (rouge) est active, son temporisateur `3s/X2` commence à compter, la fenêtre Outputs affiche le feu rouge.*

*File > Export > C++ GRAFCET*, `GermanTrafficLights.hpp`. Les parties intéressantes des 387 lignes :

```c++
namespace german_traffic_lights {

//! \brief Inputs read by the receptivities: written by the program.
struct Inputs
{
    int none = 0;
};

//! \brief Outputs of the actions: read by the program.
struct Outputs
{
    bool Green_LED = false; // Green LED
    bool Red_LED = false; // Red LED
    bool Yellow_LED = false; // Yellow LED
};

class Grafcet
{
public:

    Inputs in;
    Outputs out;
    //! \brief Active steps of each graph.
    bool X0[4] = {}; // German traffic lights

    Grafcet() { reset(); }
    void reset();                  // the initial situation
    bool cycle(float const dt);    // one cycle, dt seconds after the previous one
    float time() const;            // seconds since reset()

private:

    // Receptivities.
    bool R0_0() { return timer(0); } // German traffic lights T0: 3s/X0
    bool R0_1() { return timer(1); } // German traffic lights T1: 1s/X1
    bool R0_2() { return timer(2); } // German traffic lights T2: 3s/X2
    bool R0_3() { return timer(3); } // German traffic lights T3: 1s/X3
    ...
```

et le cœur, la recherche de la situation stable :

```c++
    // Fire the transitions that can, all graphs together, until none can.
    bool evolve()
    {
        for (int evolution = 0; evolution < 256; ++evolution)
        {
            bool any = false;
            bool F0[4];
            F0[0] = R0_0() && X0[0] && !m_forced[0];
            any |= F0[0];
            ...
            if (!any)
                return true;
            // Deactivate the upstream steps, then activate the downstream ones.
            if (F0[0]) { X0[0] = false; }
            ...
            if (F0[0]) { X0[1] = true; GRAFCET_FIRED(0, 0); }
            ...
        }
        return false;
    }
```

L'interface de la classe :

| Membre | Rôle |
|--------|------|
| `in` | les entrées, en `int` (un bouton vaut 0 ou 1, un capteur n'importe quel entier), avec leurs valeurs initiales du fichier ; écrites par le programme |
| `out` | les sorties, en `bool`, une par nom d'action ; lues par le programme |
| `X0[]`, `X1[]` ... | les étapes de chaque graphe, dans l'ordre du document (`X0` est le premier graphe) |
| `cycle(dt)` | un cycle, `dt` secondes après le précédent : le temps passe (temporisations, délais, actions temporisées), ordres de forçage, évolution jusqu'à stable, actions. Renvoie `false` quand aucune situation stable n'est atteinte |
| `reset()` | retour à la situation initiale |
| `time()` | secondes depuis `reset()` |

L'espace de noms est le nom du fichier (`gemma_dryer` pour `GEMMA-Dryer.hpp`). Le code n'utilise aucune bibliothèque, pas même la standard, et seulement C++11 : il se compile pour un AVR.

### 2.5 Sur un Arduino

Copiez l'en-tête à côté du sketch. Chaque période : lisez les capteurs dans `in`, appelez `cycle()` avec le temps écoulé, écrivez `out` vers les actionneurs. Pour le séchoir du [chapitre 10](10-GEMMA.md) (`GEMMA-Dryer.hpp`, trois graphes, entrées `Ack`, `Auto`, `EStop`, `Left`, `Manual`, `Rearm`, `Right`, `Start`, `Stop`, `Temperature`, sorties `Heat_Oven`, `Left_Motor`, `Right_Motor`) :

```c++
#include "GEMMA-Dryer.hpp"

gemma_dryer::Grafcet grafcet;
unsigned long last = 0;

void setup()
{
    pinMode(2, INPUT_PULLUP);  // Start
    pinMode(3, OUTPUT);        // Left motor
}

void loop()
{
    unsigned long const now = millis();
    grafcet.in.Start = (digitalRead(2) == LOW);
    grafcet.in.Temperature = analogRead(A0) / 10;
    grafcet.cycle((now - last) / 1000.0f);   // seconds since the last cycle
    last = now;
    digitalWrite(3, grafcet.out.Left_Motor);
    delay(10);
}
```

Sur un ordinateur, la même classe tourne dans n'importe quelle boucle : un thread, un timer Qt ou ROS, une simulation.

### 2.7 Le déboguer

Compilez avec `-DGRAFCET_DEBUG` : le code publie ses tirs, ses étapes, ses entrées et sorties, et l'éditeur affiche le GRAFCET en marche sur la carte ([chapitre 13](13-Debugging.md#6-follow-generated-grafcet-code)) :

| Où tourne le code | Comment il publie |
|-------------------|-------------------|
| un ordinateur | ZeroMQ PUB sur `tcp://*:5556` (lier avec `-lzmq` ; définir `GRAFCET_DEBUG_ENDPOINT` pour changer) |
| un Arduino (`ARDUINO` défini) | un objet JSON par ligne sur `Serial` ; `tools/serial-bridge.py` les publie sur ZeroMQ |
| ailleurs | définir `GRAFCET_DEBUG_SEND(text)` pour envoyer chaque ligne vous-même |

## 3. Pièges

- **`cycle()` renvoie `false`** : une boucle de transitions toujours vraies (deux étapes avec réceptivités `1` entre elles). L'éditeur avertit de la même façon dans sa simulation.
- **« not a C identifier »** : renommez l'entrée dans les réceptivités (`sensor_2`).
- **Une impulsion courte est manquée** : une entrée est lue une fois par cycle ; une impulsion plus courte que la période de `loop()` peut être perdue. Utilisez une période plus courte, ou verrouillez l'entrée dans une interruption.
- **La dérive du temps** : donnez à `cycle()` le temps réellement écoulé (`millis()`), pas la période souhaitée.
